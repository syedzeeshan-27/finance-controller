# AI Finance Controller

**Razorpay Buildathon · Track 04.** One daily close for a Razorpay merchant:
settlement reconciliation, 14-day cash forecasting, and Indian tax matching
(GSTR-2B · Form 26AS · statutory payments) — folded into **one severity-ranked
exception queue** you can actually act on. A deterministic engine makes every
money decision; an **AI agent** (Claude) handles what's genuinely fuzzy —
reading messy real-world bank exports and investigating exceptions — and is
only ever believed after deterministic arithmetic proves its work.

```
      DATA SOURCES                          DECISIONS
 payments.csv      ─┐                 ┌─ matched (exact/high/medium)
 settlements.csv   ─┤   ┌─────────┐   ├─ matched_split / merged / with_discrepancy
 bank_statement.csv─┼──►│  ENGINE │──►├─ duplicate_credit
 order_book.csv    ─┘   │ 6 passes│   ├─ ambiguous_abstain   ◄─ the honest ones
                        └─────────┘   ├─ exception_missing_bank / _settlement
                             │        └─ non_settlement_credit
                             ▼
                    every decision carries: evidence · confidence tier ·
                    discrepancy breakdown · candidates with rejection reasons
```

## Run it

```
pip install -r requirements.txt -r requirements-dev.txt
streamlit run src/app.py
```

That's the whole app — the dashboard opens at **http://localhost:8501**
(daily close, actionable exception queue, forecasts, tax, benchmarks).
No API key, no network, no database needed.

To reproduce every number in this repo from a clean checkout (317 tests,
determinism proofs, all benchmarks, the real-statement run — fully offline):

```
python scripts/repro.py
```

(`scripts\repro.ps1` on Windows and `scripts/repro.sh` on Linux/macOS are
thin wrappers over the same script.)

## Headline results

Every number is regenerated by `scripts/repro.py` and frozen in [reports/](reports/).
**Every engine is graded on this project's own synthetic worlds** — a generator
with minted answer keys — **not on real Razorpay or bank data**, next to a naive
baseline run through identical parsing and grading. What that does and does not
prove is spelled out in [Limitations](#limitations--what-this-does-not-prove-and-why):

| stage | this project | naive baseline |
|---|---|---|
| Reconciliation (precision / recall / disposition) | **100% / 100% / 100%**, 30/30 correct abstentions | 97.5% / 79.2% / 74.1%, 0/30 |
| Cash forecast (balance-path error / 80%-band coverage / cash-drop alerts) | **₹77,208 = 1.8% of opening balance / 79.9% / 17 of 21 true drops caught, 2 false alarms** — daily-flow WAPE 59.1% | trailing-mean ₹1,83,033 = 4.0% / — / 0 of 21 caught |
| Tax matching (disposition / ₹ claimed falsely) | **100% / ₹0** | 51.3% / ₹1,65,084 |
| Unified close (queue recall / precision / verifier violations) | **1266/1266 / 100% / 0** | 83.1% / 48.1% / 330 |
| Real bank statement (65 messy rows) | **balance chain proven to the paisa; engine claimed nothing (0 forced matches)** — an intake + abstention proof, not a matching-accuracy result | — |

100% here means *verified behaviour on deterministic constructions* — read
[ARCHITECTURE.md](ARCHITECTURE.md#read-the-engines-100-honestly) for the honest
framing, and [Limitations](#limitations--what-this-does-not-prove-and-why) below
for what was never measured at all.

## What makes it different

- **No LLM near a decision.** Matches rest on reference evidence or exact-paise
  equality; when evidence can't separate two candidates, the engine *abstains*
  and shows a human both — and the benchmark rewards that.
- **The agent proposes, arithmetic disposes.** The intake agent maps any messy
  bank export (real one included, committed at `data/real/statement_a/`); a
  validator accepts the mapping only if the running balance reproduces
  row-by-row to the paisa. A real recorded run is committed — including one
  rejected-then-repaired proposal — and replays offline with no API key,
  request-hash-checked (`data/agent_transcripts/intake/statement_a.jsonl`).
- **Everything is independently verified.** Four verifiers share no code with
  the engines, re-read the raw files with their own parsers, and fail the run
  on any violation — including a close that misreports its own trust panel.

## Commands worth trying

```
python -m controller.close data/seeds/42 --report              # one daily close
python -m controller.close data/seeds/42 --as-of 2025-06-30 --snapshot
python -m controller.close data/seeds/42 --snapshot --report   # + "since last close" delta
python -m controller.close --merchants data/merchants.json     # multi-merchant rollup
python -m controller.queue_state data/seeds/42 list            # act on queue items from the CLI
python -m tax.gstr1 data/seeds/42 --report                     # GSTR-1 sales summary
python -m agent.intake data/real/statement_a/statement.xlsx --out out/w --mapping data/real/statement_a/world/mapping.json --report
```

Optional: put an `ANTHROPIC_API_KEY` in `.env` (template provided) to enable
**live** agent runs — `agent.intake --record` maps a brand-new bank export and
records the transcript; `agent.investigate` drafts advisory notes on queue
items. Decisions are unaffected in every mode, by test.

## Limitations — what this does not prove (and why)

Read these before the numbers above. Nothing here is buried in the design doc
on purpose; a reader should meet it first.

- **Synthetic data — allowed, and by design.** Real merchant data was not
  accessible to us, and the buildathon brief itself defines Track 04 as
  closing a finance-ops loop "across a 50+ record batch of **synthetic data**"
  ([razorpay.com/buildathon](https://razorpay.com/buildathon/)). Everything
  graded in this repo runs on worlds from `src/recon/generate.py`; the one
  real file is a bank statement (`data/real/statement_a/`).
- **The 100% figures are against our own answer keys.** Each engine is graded
  on scenarios the generator constructed, with the answer minted at generation
  time and the constants frozen before the final runs. 100% means the engine
  does exactly what those deterministic constructions demand — including
  abstaining where they are built to be undecidable. It is not a field-accuracy
  claim; real-world accuracy is unmeasured.
- **Reconciliation has never run on real Razorpay settlement data.** The only
  real-data evidence is the bank-statement intake — a narrower problem (mapping
  one messy export, proven by the running-balance chain) than matching
  settlements to bank credits. On that statement the engine correctly claimed
  nothing: that demonstrates abstention discipline, not matching accuracy.
- **Razorpay Test Mode cannot yield settlement data.** Razorpay's docs say Test
  Mode moves no real money and describe settling to a bank account only for
  Live Mode ([Test and Live Modes](https://razorpay.com/docs/payments/dashboard/test-live-modes/));
  the [Settlements FAQ](https://razorpay.com/docs/payments/settlements/faqs/)
  says nothing about test mode at all. Tested hands-on (Aug–Sep 2026):
  test-mode settlement entries were generated but only ever showed *failed*,
  never processed, whichever payment method was used. So the `src/ingest/`
  adapters are exercised only against official-schema fixtures
  (`data/fixtures/razorpay/`) — never a real live pull; `ingest.pull --live`
  exists but is unverified against a production account.
- **Real GST and TDS data need a registered business.** GSTR-2B "will be
  generated for every registered person" and is "available for viewing and/or
  downloading … in post-login mode on the GST portal"
  ([GST portal FAQ](https://tutorial.gst.gov.in/userguide/returns/FAQ_gstr2b.htm));
  a GSTIN is issued only when a registration application is approved
  ([GST registration](https://reg.gst.gov.in/registration/)). Form 26AS is
  likewise only available through the taxpayer's own income-tax login.
  `gstr2b.csv` and `form26as.csv` are therefore generated by the same world
  generator, and the tax engine's 100% is against that generated truth.
- **Forecast accuracy, in absolute terms.** The daily point forecast is not
  day-precise: 59.1% WAPE on daily net flow, a series that is spiky by
  construction. What a cash planner can use is the balance path — within
  ₹77,208 of the truth on average (1.8% of a ~₹45L opening balance; ₹1,24,750
  by day 14) — the 14-day low (within ₹30,041, dated within two days 96% of
  the time), the self-calibrated 80% band (79.9% coverage on average, but
  53–97% per world) and the cash-drop alerts: 17 of 21 true drops caught with
  2 false alarms across 70 held-out fortnights × three depths (₹2L 10/1/2 ·
  ₹3L 7/1/0 · ₹4L 0/2/0 hits/misses/false alarms). That is a small sample by
  nature, and most true drops are the same calendar fortnight — the one
  holding the 1st-of-month payroll + rent cluster — across worlds, so they are
  less independent than the count suggests. Every event is listed per origin
  in `reports/forecast_backtest.md`.
- **Scale.** ~8k records/s is measured on generated worlds of a few thousand
  records on a laptop, not on production volumes.
